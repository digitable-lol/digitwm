# Workbench themes: where they come from

**Русская версия: [themes.ru.md](themes.ru.md).**

Not one colour scheme here is written by hand, and none of them lives in this
repository. The theme files for thirteen targets - vim, neovim, tmux,
alacritty, kitty, zsh, starship, fzf, eza, bat, btop, delta, lazygit - are
generated by Digitable Workbench from a single palette file;
`session/install.sh` lays them out and substitutes the same colours into
`cwmrc`, `Xresources` and `polybar.ini`. The reason is in `session/README.md`,
"The rule that cannot be broken": no third-party code and no third-party
licences go in here, and duplicating one palette across thirteen formats is a
way to let the colours drift apart on one careless patch.

Which raises the question the documentation never answered: **where does the
installer get those files on a machine where Workbench was never cloned?**

## Three sources, in order of preference

| | Source | How it is chosen |
| --- | --- | --- |
| 1 | A local Workbench clone | by itself, if found |
| 2 | Any themes directory | `--themes-dir DIR`, `--palette-file FILE` |
| 3 | The open portal | `--fetch-configs`, and only if 1 and 2 came up empty |

**The first.** The installer looks for Workbench's `bootstrap.sh` in four
places (`../courses/…`, `~/projects/courses/…`, `~/courses/…`,
`~/.local/share/digitable-workbench/…`) and for a themes directory next to it.
The test is a `vim/` subdirectory, and the directory that passes it is
`products/workbench/tmp/generated/themes` - **a build artefact of somebody
else's repository**. `products/workbench/themes/` fails the test: it has no
`vim/` inside. So the first source works for whoever built Workbench next
door, which is the author of digitwm rather than its user.

**The second.** `--themes-dir` and `--palette-file` take any directory: an
unpacked archive, a copy from another machine, your own palette. The installer
assumes nothing about where it came from.

**The third.** On a clean machine neither of the first two exists, and until
now that meant: no palette substituted, the `#@palette-begin…#@palette-end`
block cut out of the templates, no `Xresources` and no `polybar.ini` written at
all, and `session/verify.sh` failing eleven checks and returning 1. The configs
are open and they are online:

```
https://courses.digitable.life/workbench/configs/index.json
https://courses.digitable.life/workbench/configs/<target>.json
```

Fifty targets, three palettes (`carbon`, `paper`, `signal`), no token and no
payment. A target looks like `{id, version, shared:[…], palettes:[{id, label,
files:[{name, path, lang, bytes, lines, text}]}]}`, where `text` is the whole
file. The `path` field is exactly what `install_theme` lays out:
`vim/colors/digitable-focus-carbon.vim`, `bat/Digitable-Focus-Carbon.tmTheme`
and so on.

## The line: nothing is fetched silently

The comment in `session/install.sh` above the Workbench search has not changed
by one word:

> we download nothing from the network: an installer quietly pulling somebody
> else's file is exactly what `curl | sh` is scolded for.

So the third source is **behind a flag**. Without `--fetch-configs` the
installer makes no network request at all, and the default has not moved an
inch: no themes on disk means no themes, stated in the run header and in the
next steps. The flag itself is the consent; what it downloads lands in the
`~/.local/state/digitwm/workbench-configs` cache and changes nothing in the
system.

Which source a given run picked is visible in the header, `--plan` included:

```
  темы из     : /home/…/.local/state/digitwm/workbench-configs
                (открытый портал https://courses.digitable.life/workbench/configs (--fetch-configs))
```

and the plan carries a line of its own: `[сеть] скачать 13 целей и палитру
carbon с …`.

## The palette is not published, yet it is all there

`focus-palettes.json` at that address returns **404**: the palette is not
published as a file of its own. It is published inside the themes:

- the **helix** theme (`digitable-focus-<palette>.toml`) ends with a
  `[palette]` block holding fifteen colours **under the very names** the
  installer expects: `background`, `surface`, `surfaceRaised`, `foreground`,
  `muted`, `subtle`, `border`, `accent`, `accentSoft`, `blue`, `green`,
  `yellow`, `orange`, `purple`, `red`;
- the **alacritty** theme supplies the remaining two: `terminalBlack` is
  `colors.normal.black`, `terminalBrightBlack` is `colors.bright.black`.

Out of those `fetch_palette` assembles a `focus-palettes.json` of the shape
`load_palette` already reads. No hexadecimal code appears in our files in the
process - every one of them comes from the portal.

**Checked against the canonical file.** The assembled palette was compared with
`products/workbench/themes/focus-palettes.json` from a Workbench clone: all
**17 keys for each of the three palettes** matched. So did the theme files -
all 18 downloaded ones byte for byte with what sits in the clone's
`tmp/generated/themes`.

Two keys the installer never reads do not match: `selection` and
`lineHighlight` arrive from the helix theme already flattened against the
background (`#0F3745` against `#15566A99` in the canonical file). They cannot
be compared with it, and no session template substitutes them.

Should the portal's format change - the `[palette]` block disappear, or the
terminal blacks move - the palette will not assemble, and that will be said in
a warning rather than papered over with a default.

## The numbers

Installing into an isolated prefix on a machine with no Workbench clone, with
`session/verify.sh` right after:

| Run | passed | failed | exit |
| --- | --- | --- | --- |
| no flag | 37 | 11 | 1 |
| `--fetch-configs` | 49 | 0 | 0 |
| `--themes-dir` from a local clone | 49 | 0 | 0 |
