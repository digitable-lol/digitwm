# digitwm на macOS: поставить, запустить и что именно сломается

**English version: [macos-install.md](macos-install.md).**

[macos.ru.md](macos.ru.md) — это план переноса: этапы, потери, числа, при
которых перенос закрывают. Здесь другая половина: что человек с маком набирает,
что видит, какое разрешение у него спросят и — то, о чём обычно молчат, — что
скорее всего откажет при первом запуске и как узнать, какой именно вызов Apple
это сделал.

**2 сентября 2026 года digitwm впервые собрали и запустили на настоящем маке.**
До этого дня здесь стояло «мака нет ни у кого в проекте», и это было правдой
полгода. Что известно теперь и откуда — по порядку, потому что источники разные
и стоят они разного:

| Где | Что там прошло |
|---|---|
| **Мак владельца**, 2 сентября 2026: Apple Silicon, `/opt/homebrew`, **3 дисплея**, сборка `HEAD-bfd5d85` через `brew install --HEAD` | Сборка, запуск, разрешение Accessibility, и `digitwm -N`: **ответили все 12 вызовов Apple, 0 отказов** — включая запись геометрии, поднятие окна и захват `CM-h`. **10 окон** взято на ленту. |
| **Маковские бегунки GitHub**, обе архитектуры, на каждый толчок в дерево | Сборка из `macos/Makefile`: **0 ошибок компилятора, 0 предупреждений** на обеих. Подпись, `-k`, `-n`, `-N`, пакет `.app`, повторимая выпускная сборка. |
| **Linux**, на каждый толчок | Всё, чему мак не нужен: `macos/check.sh` (лента поверх порта против ленты поверх X11) и `macos/stub-build.sh` (согласованность двух файлов на Objective-C с заглушкой API). |

**Чего не проверял никто, и это надо держать в голове, читая всё ниже.**
`digitwm -N` двигает окно ровно туда, где оно и было, — значит настоящая
раскладка под нагрузкой (десять окон разъезжаются по колонкам, человек жмёт
клавиши, приложения открывают и закрывают окна) на маке ещё **не работала ни
разу**. И известен один живой отказ: **горячие клавиши регистрируются, но не
действуют** — `-N` говорит «`RegisterEventHotKey answered CM-h taken`», а
Control-Option-H не делает ничего. Разбирается это ключом `-v`; см. «Когда не
работает».

## Что набрать

Одно из трёх, что удобнее.

**Из клона, вместе со всем окружением:**

```sh
git clone https://github.com/digitable-lol/digitwm
cd digitwm
sh bootstrap.sh
```

На маке `bootstrap.sh` собирает маковскую цель, а не X11-сборку, и ставит
`digitwm` в `~/.local/bin`. Ему нужны Xcode Command Line Tools и больше ничего
— ни пакетов из brew, ни yacc, ни pkg-config, ни заголовков X11. Если
инструментов нет, он это скажет и остановится: `xcode-select --install`.

**Только оконный менеджер, из клона:**

```sh
make -C macos
sudo make -C macos install          # /usr/local/bin/digitwm
```

**Из brew:**

```sh
brew tap digitable-lol/digitwm https://github.com/digitable-lol/digitwm
brew install --HEAD digitable-lol/digitwm/digitwm
```

Этим путём — `brew install --HEAD` — маковская цель и была впервые собрана на
настоящем маке 2 сентября 2026: в `Cellar` легло `digitwm/HEAD-bfd5d85`, а на
`PATH` — ссылка `/opt/homebrew/bin/digitwm`. Разница между ссылкой и настоящим
файлом не косметическая: разрешение Accessibility система помнит по настоящему
файлу, и первый же час на маке ушёл на это. См. «Когда не работает».

## Что видно при первом запуске

```
$ digitwm
```

1. macOS поднимает свой диалог: «digitwm хочет управлять этим компьютером с
   помощью функций универсального доступа». Ни одно окно ещё не тронуто. Apple
   про этот вызов пишет прямо, что запрос «происходит асинхронно и не влияет на
   возвращаемое значение», — поэтому следующее, что вы увидите:
2. digitwm говорит, что разрешения у него нет, называет, где выключатель, и
   выходит. Это не сбой: разрешение читается один раз, при запуске.
3. Вы включаете digitwm в **Системные настройки → Конфиденциальность и
   безопасность → Универсальный доступ** и запускаете снова.
4. `digitwm: 31 window(s) on the ribbon.` — и все открытые окна выстраиваются в
   колонки. Дальше процесс молчит, пока вы не нажмёте клавишу или не откроете
   окно.

**В Dock ничего не появляется, строки меню тоже нет.** У digitwm нет
собственного окна: он расставляет чужие. Остановить — Control-Option-Q или
Control-C в терминале, из которого он запущен.

**Запускать из терминала в вошедшем графическом сеансе.** Не по ssh и не из
демона launchd: процесс без связи с оконным сервером не может забрать
комбинацию клавиш, и digitwm говорит об этом словами, а не запускается глухим.

## Два разрешения, и почему спрашивают одно

Apple делит права на клавиатуру и окна надвое, и деление не то, которого ждёшь.
Из сессии WWDC, где это ввели: «там, где приложению, только слушающему события,
нужно разрешение на мониторинг ввода, приложению, изменяющему события, нужно
разрешение на универсальный доступ».

| Что делает программа | Что macOS спросит у пользователя |
|---|---|
| читает и пишет чужие окна через Accessibility API | **Универсальный доступ** |
| смотрит все клавиши через `CGEventTap`, даже ничего не меняя | **Мониторинг ввода** — другой выключатель, другой диалог |
| забирает одну комбинацию через `RegisterEventHotKey` | ничего |

Первое digitwm нужно, потому что двигать чужое окно — это оно и есть. Второго он
избегает тем, что берёт клавиши через `RegisterEventHotKey`, а не через event
tap; довод целиком — в шапке `macos/wsi_key.m`. Итого: **одно разрешение,
спрошенное один раз.**

Цена этого выбора записана, а не спрятана:

- `RegisterEventHotKey` — это Carbon, и инженеры Apple сами говорят, что честно
  рекомендовать его не могут: «намертво привязан к устаревшему Carbon
  toolbox». Современной замены, которая проглатывает клавишу без второго
  разрешения, нет.
- **macOS Sequoia отказывает горячей клавише, у которой из модификаторов только
  Shift и Option.** Таблица по умолчанию везде использует Control-Option и под
  запрет не попадает; строка `bind-key M-h ...` в `digitwmrc` — попадает, и digitwm
  предупреждает на этой строке, а не даёт отказу случиться молча.

Есть третье разрешение, которого digitwm не просит намеренно: **запись экрана**.
Содержимое окон он не читает, только прямоугольники.

## Клавиши

```
$ digitwm -k
```

печатает живую таблицу. По умолчанию:

| Клавиши | Что происходит |
|---|---|
| ⌃⌥ H / L | фокус на колонку левее / правее |
| ⌃⌥ K / J | фокус на окно выше / ниже в колонке |
| ⌃⌥⇧ H / L | унести окно в соседнюю колонку |
| ⌃⌥⇧ K / J | унести окно вверх / вниз по своей колонке |
| ⌃⌥⌘ H / L | поменять колонку местами с соседней |
| ⌃⌥ R | перебрать четыре ширины колонки |
| ⌃⌥ = / − | шире / уже |
| ⌃⌥ C | поставить ленту серединой на текущую колонку |
| ⌃⌥ F | снять окно с ленты в плавающий слой и обратно |
| ⌃⌥ Q | остановить digitwm |

**Это не те клавиши, что в X11, и так сделано намеренно.** `conf.c:280`
привязывает ленту к Mod4, «потому что upstream cwm оставляет её полностью
свободной». На маке Mod4 — это Command, то есть ровно наоборот, а регистрация
горячей клавиши забирает комбинацию у **всех** приложений сразу. Порт,
сохранивший X11-таблицу, при первом же запуске отобрал бы у всего стола
Command-H, Command-J, Command-K, Command-L, Command-C, Command-F, Command-R,
Command-минус и Command-равно. Control-Option — то, что macOS не трогает сам.

Вернуть X11-клавиши можно, записав их в `~/.digitable/digitwm/digitwmrc`; буквы
модификаторов те же, что уже описаны в `cwmrc(5)`:

| Буква | X11 | macOS |
|---|---|---|
| `S` | Shift | ⇧ Shift |
| `C` | Control | ⌃ Control |
| `M` | Mod1 (Alt) | ⌥ Option |
| `4` | Mod4 | ⌘ Command |
| `5` | Mod5 | — ничего; у мака их четыре |

Привязка на одном Command получит строку предупреждения о том, что она сделает с
остальной машиной. И всё равно будет выполнена.

## Какой файл читается и что из него

digitwm читает **тот же файл, что и X11-сборка**, и находит его тем же
поиском, — чтобы один файл описывал обе машины. Порядок, от сильного к
слабому:

| | файл | |
|---|---|---|
| 1 | названный ключом `-c` | сильнее всего остального |
| 2 | `$DIGITWMRC` | если переменная задана и непуста |
| 3 | `~/.digitable/digitwm/digitwmrc` | своё имя в каталоге, где это семейство инструментов держит настройки |
| 4 | `~/.cwmrc` | имя cwm: читается, чтобы конфигурация, написанная для cwm, продолжала работать, — и об этом говорится вслух, один раз, в stderr |

Порядок написан один раз — `confpath.c`, — и компилируется в оба двоичных
файла, а не переписан дважды; `tools/check-config-order.sh` задаёт обоим одни и
те же семь вопросов на каждый push. Мак, который молча читал бы не тот файл,
что рабочая станция, превратил бы «один файл описывает обе машины» в
предложение и только.

Прочитать весь этот файл он не может. В `cwmrc(5)` **34 директивы**; digitwm
выполняет **9**, а остальные **25** называет вслух, с причиной, на той строке,
где они стоят:

```
$ digitwm -n
/Users/you/.digitable/digitwm/digitwmrc: 12 directive(s): 6 taken, 5 X11's alone, 1 not understood
```

**Выполняются (9):** `ribbon`, `ribbonhide`, `ribbonwarp`, `ribbongap`,
`ribbonminwidth`, `ribbonminheight`, `ribbonwidths`, `bind-key`, `unbind-key`.

**Только X11 (25)**, по причинам — все четыре решены в
[macos.ru.md](macos.ru.md) до того, как всё это было написано:

- **на чужом окне нечего рисовать рамкой** — `borderwidth`, `activeborder`,
  `inactiveborder`, `urgencyborder`, `groupborder`, `ungroupborder`, `color`;
- **нет меню** — `font`, `fontname`, `selfont`, `menubg`, `menufg`;
- **нет групп**, потому что у Spaces нет публичного API — `sticky`,
  `autogroup`;
- **нет захвата указателя и нет EWMH** — `bind-mouse`, `unbind-mouse`,
  `snapdist`, `moveamount`, `htile`, `vtile`, `gap` (у
  `NSScreen.visibleFrame` Dock и строка меню уже вычтены, вычитать нечего),
  `command`, `wm`;
- **порт не читает класс окна** и потому не может сопоставить — `ignore`,
  `ribbonrule`.

Последняя пара — единственная в списке, которая является дырой, а не потерей.
`ribbonrule` кладёт названное приложение в выбранную колонку; на macOS для этого
нужен ещё один вызов через границу — спросить у окна заголовок или приложение, —
а `macos/wsi_platform.h` намеренно шириной в одиннадцать вызовов. Это названо
здесь, а не выдано за работающее.

`ribbonwarp yes` принимается и ничего не делает, о чём и сообщает: этот порт не
умеет двигать указатель вовсе. `wsi.h` разрешает ровно это — при условии, что и
фокус за указателем не ходит, — и порт берёт пару целиком.

Из **124 команд**, которые `bind-key` может назвать на X11 (`conf.c`,
`name_to_func`), здесь существуют **16**: пятнадцать команд ленты и `quit`.
Остальные просят рамку, группу, меню, перенос указателя или свойство EWMH.
Шестнадцать печатает `digitwm -k`.

## Когда не работает — узнать, какое имя отказало

```
$ digitwm -N
```

проходит по всем вызовам Apple, которые делает порт, в том порядке, в каком
доходит до них при работе, и печатает, кто ответил. **Ниже — не пример, а
настоящий вывод** с мака владельца, 2 сентября 2026, Apple Silicon, три
дисплея:

```
  [1] AXIsProcessTrustedWithOptions                  answered Accessibility granted
  [2] +[NSScreen screens], -frame, -visibleFrame     answered 3 display(s), first "P27FBA-RAGL" 1920x1080, workable 1920x1049
  [2] -[NSScreen localizedName]                      answered P27FBA-RAGL
  [2] NSWorkspace, NSRunningApplication              answered 10 window(s) taken onto the ribbon
  [2] +[NSEvent mouseLocation]                       answered pointer at 374,661
  [1] AXUIElementCopyAttributeValue (position, size) answered first window at -1996,31 956x1049
  [2] AXUIElementIsAttributeSettable, SetAttributeValue answered geometry accepted
  [2] AXUIElementPerformAction, kAXRaiseAction       answered raise accepted
  [2] kAXMainAttribute, kAXFrontmostAttribute        answered activation accepted
  [-] wsip_pointer_warp                              answered refuses, as designed: no call for it exists
  [2] InstallEventHandler, GetApplicationEventTarget answered handler installed
  [2] RegisterEventHotKey                            answered CM-h taken

0 call(s) did not answer.
```

Двенадцать из двенадцати. Обратите внимание на `-1996` — это окно на мониторе
**слева** от главного; отрицательные координаты для порта нормальны и
обрабатываются знаковой арифметикой, но ни один вектор в дереве их до сих пор
не проверял (`fts/vectors/layout.json`, `macos/runcheck.c` — все начала
неотрицательны).

Для сравнения, тот же `-N` на маковском бегунке GitHub, где нет ни человека, ни
настоящих окон: разрешение там выдано, но **два вызова из двенадцати
отказывают** — `SetAttributeValue` («the write was refused») и `kAXRaiseAction`
(«raising was refused»). То есть окно, которое там нашлось, читается и не
пишется. Это не поломка порта, а то, чем виртуальный дисплей бегунка
отличается от стола: полезно знать, читая любой отчёт с бегунка.

Строка `FAILED` называет вызов, а не симптом. Её и надо сообщать, а дальше в
этом разделе написано, чего стоит каждый.

### Разрешение выдано, а его всё равно нет

Первый час на настоящем маке ушёл именно на это: разрешение выдано digitwm, а
digitwm говорит, что его нет. Причин три, и `-N` теперь называет их **сам, до
первого вызова** — этим строкам разрешение не нужно:

```
This process, before any of that:
  running   /opt/homebrew/Cellar/digitwm/HEAD-bfd5d85/bin/digitwm
  launched  /opt/homebrew/bin/digitwm
            NOT THE SAME FILE. ...
  started by /Applications/Ghostty.app/Contents/MacOS/ghostty (pid 4711)
            If that is a terminal, the permission macOS looks at is ITS ...
  signature ad-hoc (a hash of this very file)
            cdhash 0ab83fd244a251e850d1c29ea6ae2d363ebe8478
```

**1. Запущен из терминала.** macOS приписывает разрешение не программе, а тому,
что Apple называет *responsible code*. Инженер Apple DTS перечисляет случаи
прямо: «Run by the user from Terminal — **The tool's responsible code is
Terminal**»; «Run by `launchd` as a daemon or agent — If the daemon or agent was
installed by `SMAppService`, that makes the app the responsible code. Otherwise,
the daemon or agent should include `AssociatedBundleIdentifiers` in its
`launchd` property list»
([developer.apple.com/forums/thread/756510](https://developer.apple.com/forums/thread/756510)).
Там же Apple оговаривает: «The exact algorithm it uses is not documented, has
changed in the past, and may well change in the future». Значит: **дать
разрешение терминалу** (Terminal, iTerm, Ghostty) и закрыть терминал целиком —
Command-Q, а не вкладку. Прямой фразы «grant it to the terminal» Apple не
пишет; это следствие процитированного правила, и его же повторяют чужие
инструменты того же рода.

**2. brew кладёт на PATH ссылку.** `/opt/homebrew/bin/digitwm` — символическая
ссылка на файл в `Cellar`. Разрешение помнится по настоящему файлу. `-N`
печатает оба пути и говорит вслух, когда они разошлись.

**3. Пересобрано после выдачи.** Разрешение система помнит по подписи. Apple,
TN3127: «**Ad hoc signed code**, called Sign to Run Locally by Xcode, **has a DR
but it's tied to that specific version of the code** ... If you tweak the code
and run it again, macOS repeats that prompt»
([TN3127](https://developer.apple.com/documentation/technotes/tn3127-inside-code-signing-requirements)).
Лечится постоянным удостоверением: `make -C macos SIGNID="имя сертификата"`.
Пакет `.app` этого **не** лечит: там же Apple объясняет, что имя пакета —
только слагаемое внутри требования, а само требование у ad-hoc — `cdhash H"…"`.

**Что чинит пакет, а что нет.** Пакет чинит первое: приложение, запущенное из
`/Applications`, — само себе ответственное. Apple: «If you nest your tool, or
your background-only app, within a standard app then the system will **likely**
consider that app to be responsible for your process»
([thread/680491](https://developer.apple.com/forums/thread/680491); «likely» —
слово Apple, не наше). Третьего пакет не чинит совсем.

**Про перезапуск.** Заголовок Apple `AXUIElement.h` говорит про запрос ровно
одно: «Prompting occurs asynchronously and does not affect the return value».
Что состояние прав кэшируется и что после выдачи программу надо перезапустить,
**Apple нигде не пишет**; это сходящийся опыт чужих менеджеров — yabai: «The
application must be restarted after access has been granted», skhd: то же
слово в слово. Мы повторяем это как опыт, а не как документированное поведение.

**И отдельная ловушка версии системы.** Тот же инженер Apple, январь 2026: «The
inability to add a standalone executable to System Settings > Privacy & Security
is a known regression in macOS 26.1. It's fixed in our 26.3 beta seeds»
([thread/813989](https://developer.apple.com/forums/thread/813989)). На 26.1 и
26.2 добавить голый двоичный файл в список может быть невозможно вовсе — и это
ещё один довод дать разрешение терминалу или поставить пакет.

### Клавиша зарегистрирована и не действует

Живой отказ, найденный на маке владельца: `-N` говорит `RegisterEventHotKey
answered CM-h taken` и `InstallEventHandler ... answered handler installed`, а
Control-Option-H не делает ничего.

Между нажатием и движением ленты четыре места, где нажатие пропадает, и снаружи
все четыре выглядят одинаково. Разбирается это ключом:

```
$ digitwm -v 2>/tmp/digitwm.log
```

Что искать в выводе, по порядку:

1. `carbon: handler entered` — **есть или нет**. Нет — событие до процесса не
   дошло, и лента ни при чём; смотреть надо на `macos/wsi_key.m` и на то, что
   процесс без пакета `.app` не получает событий Carbon. Соседние строки
   печатают, чем процесс оказался для системы: политику активации и
   идентификатор пакета.
2. `key: id N = C-M-h -> ribbon-focus-left ARRIVED in this process` — событие
   опознано и превращено в команду.
3. `key: before` и `key: after` с номером окна, которое держит клавиатуру, —
   если номер не изменился, команда отработала вхолостую.
4. Дамп состояния: каждый выход с началом и размером, каждая лента с числом
   колонок и признаком `attached`/`DETACHED`, каждое окно с координатами и
   лентой, на которую оно легло. Здесь видно, если при трёх дисплеях окна
   привязались не к тому экрану, — фокус тогда ездит по ленте, на которую никто
   не смотрит.

`DIGITWM_TRACE=1` делает то же для digitwm, поднятого через `launchd` или из
Finder, где ключ поставить некуда.

**Чего `-N` поймать не может, и что ловит вместо него.** Опечатка в имени или
неверный список аргументов до запуска не доживают: они падают при первой же
встрече файла с настоящими заголовками Apple — ошибка компиляции с номером
строки, до того как что-то произойдёт с чьими-то окнами. Первая такая встреча
состоялась 2 сентября 2026 на маковских бегунках GitHub и дала **0 ошибок и 0
предупреждений** на обеих архитектурах.

### Три предсказания и что из них вышло

Пока мака не было, здесь стояли три вещи, которые «откажут первыми». Две из
трёх не отказали, одна отказала — и не та, на которую ставили. Предсказания
оставлены вместе с приговорами: документ, который стирает свои промахи, нечем
проверять.

| Предсказывали | Что вышло | Где измерено |
|---|---|---|
| **`macos/wsi_key.m` не соберётся** — справочника Carbon Event Manager у Apple больше нет, си-объявлений она не публикует, заглушка написана по swift-проекции | **Собрался.** Оба файла на Objective-C, `wsi_ax.m` и `wsi_key.m`, — **0 ошибок, 0 предупреждений** против настоящих заголовков Apple, с первого раза, на обеих архитектурах | Маковские бегунки GitHub, 2 сентября 2026 |
| **Клавиши регистрируются и не приходят** — программа без пакета `.app`, а про доставку событий Carbon такой программе Apple не пишет ничего | **Отказало ровно это.** Регистрация проходит (`RegisterEventHotKey answered CM-h taken`), нажатие ничего не делает. Причина пока не названа числом — на это заведён ключ `-v` | Мак владельца, 2 сентября 2026 |
| **Активация отвергнута** — тип значения для `kAXMainAttribute`/`kAXFrontmostAttribute` Apple не документирует, `kCFBooleanTrue` был догадкой | **Не отвергнута.** `activation accepted`. Догадка оказалась верной | Мак владельца, 2 сентября 2026 |

Про второе Apple с тех пор нашлась цитата, и она не в нашу пользу: инженер DTS
про `RegisterEventHotKey` — «However, it's **intimately tied to the legacy
Carbon toolbox** and thus I can't honestly recommend it», и советует
`CGEventTap` с `CGPreflightListenEventAccess`
([thread/735223](https://developer.apple.com/forums/thread/735223)). Там же он
описывает нужную форму приложения с горячими клавишами — вложенное приложение с
`LSUIElement`. Цена перехода на `CGEventTap` названа в этом же документе выше:
второе разрешение, «Ввод с клавиатуры», второй диалог и вторая строка в
системных настройках. Решение — за владельцем, и принимать его надо после того,
как `-v` скажет, где именно пропадает нажатие, а не вместо этого.

### Чего стоит каждый отказ

| Что отказало | Что перестаёт работать | Что работает всё равно |
|---|---|---|
| `AXIsProcessTrustedWithOptions` | всё | ничего — это и есть разрешение |
| `NSWorkspace` / `NSRunningApplication` | окна не находятся вообще | ничего |
| `NSScreen screens` / `frame` | ленты нет: её негде разложить | ничего |
| `NSScreen localizedName` | два одинаковых монитора становятся одним именем и одной лентой | один монитор |
| `AXUIElementCopyAttributeValue` | порт не читает прямоугольник окна | ничего |
| `AXUIElementIsAttributeSettable` / `SetAttributeValue` | окна никогда не двигаются | раскладка считается и не применяется |
| `AXUIElementPerformAction` (raise) | перекрывающиеся окна остаются не в том порядке | колонки, которые не перекрываются |
| `kAXMainAttribute` / `kAXFrontmostAttribute` | клавиатура не идёт за фокусом | вся раскладка |
| `RegisterEventHotKey` | нет команд | расстановка окон по мере открытия и закрытия |
| `AXObserverRemoveNotification` | ушедшее окно стоит немного лишней работы | всё |
| `CFRunLoopRemoveSource` | у закрытого приложения течёт наблюдатель | всё |

## Доставка и ловушка в ней

**Mac App Store для этой программы закрыт правилом самой Apple.** Apple
перечисляет «использование accessibility API в ассистивных приложениях» среди
запрещённого в песочнице, а магазин без песочницы не принимает. Значит digitwm —
обычный исполняемый файл со вшитым в секцию `__TEXT,__info_plist` `Info.plist`
(та форма, которую Apple документирует для однофайловых инструментов), и его
дорога — brew.

**Ловушка: разрешение запоминается по подписи.** `make -C macos` подписывает
ad-hoc (`codesign --sign -`), а ad-hoc-подпись — это хеш двоичного файла, то
есть каждая пересборка для macOS уже другая программа, и диалог возвращается.
Пересобирать дважды в день — отвечать на него дважды в день. Apple пишет это
прямо (TN3127, процитировано выше). У выпущенного файла подпись одна на всю
версию, и `brew reinstall` той же версии разрешения не теряет; переход на
следующую версию — теряет, и иначе не бывает.

**Вторая ловушка, найденная сборкой:** `codesign`, встретив в каталоге
`Info.plist` с `CFBundleExecutable`, подписывает **каталог**, а не файл —
первая же сборка на бегунке дала `Format=app bundle` и печать на 42 файла
каталога `macos/`. Файл, вынесенный из такого каталога (а формула его выносит),
остаётся с подписью, которой не на что опереться. Поэтому `macos/Makefile`
линкует и подписывает в `${OBJDIR}`, где никакого `Info.plist` нет, и падает,
если подпись всё-таки вышла пакетной.

**И третья, про пакет:** `digitwm` и `digitwm.app/Contents/MacOS/digitwm` — одна
и та же программа, но **разные `cdhash`**: подписывая пакет, `codesign`
переподписывает лежащий внутри файл. Значит разрешение, выданное файлу, и
разрешение, выданное пакету, — два разных разрешения, и одно не считается за
другое.

Выход — своё постоянное удостоверение подписи. Создать самоподписанный
сертификат Code Signing в «Связке ключей» (Ассистент сертификации → Создать
сертификат, тип *Подпись кода*), затем:

```sh
make -C macos SIGNID="Имя вашего сертификата"
```

— и разрешение переживает пересборки. Это обычная практика ровно для этой
задачи, и она ни разу не была выполнена в этом проекте.

## Чего не будет

Шесть из этого разобраны в [macos.ru.md](macos.ru.md) — измерением или
названным отсутствием, — и ни одно не является временным состоянием работы:

1. **окно дёрнется.** Оно появляется там, куда его поставило приложение, и уже
   потом уезжает в свою колонку: у macOS нет аналога `MapRequest` из X11, а
   `AXObserverCallback` объявлен `void`;
2. **`ribbonhide` оставляет полоску в 1 пиксель.** macOS не даёт увести окно за
   экран целиком;
3. **групп нет.** У Spaces нет публичного API;
4. **полноэкранное окно не на ленте.** Оно живёт в своём Space, и политика
   вставки это уже предусматривала;
5. **родные вкладки ломаются.** Terminal.app со вкладками — одно окно для
   Accessibility API и несколько для вас;
6. **у активного окна нет рамки.** На чужом окне рисовать нельзя. Как ещё
   отмечать окно с фокусом — отдельное решение владельца, не часть этого
   переноса.

И два, которые добавляет этот документ:

7. **указатель никогда не переносится за фокусом** — вызова для этого в
   публичном API нет, и фокус за указателем тоже не ходит. Одно решение, обе
   половины;
8. **окно приложения, которого секунду назад не было запущено, попадает на
   ленту с опозданием до секунды.** Порт спрашивает, кто запущен, по часам, а
   не подпиской, и шапка `macos/wsi_ax.m` говорит почему, чего это стоит и
   какие два документированных имени извещений это заменяют.
