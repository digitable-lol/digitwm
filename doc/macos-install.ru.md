# digitwm на macOS: поставить, запустить и что именно сломается

**English version: [macos-install.md](macos-install.md).**

[macos.ru.md](macos.ru.md) — это план переноса: этапы, потери, числа, при
которых перенос закрывают. Здесь другая половина: что человек с маком набирает,
что видит, какое разрешение у него спросят и — то, о чём обычно молчат, — что
скорее всего откажет при первом запуске и как узнать, какой именно вызов Apple
это сделал.

**Мака нет ни у кого в проекте** (`portability.md:13`). Всё ниже, что описывает
мак, — описание того, о чём код просит мак, а не отчёт о том, как это
произошло. Раздел «Что проверено здесь, а что не проверено нигде» показывает
границу между этими двумя вещами, в числах.

## Что набрать

Одно из трёх, что удобнее.

**Из клона, вместе со всем окружением:**

```sh
git clone https://github.com/digitable-lol/digitwm
cd digitwm
sh bootstrap.sh
```

На маке `bootstrap.sh` собирает маковскую цель, а не X11-сборку, и ставит
`digitwm` в `~/.local/bin`. Ему нужны Xcode Command Line Tools и больше ничего
— ни пакетов из brew, ни yacc, ни pkg-config, ни заголовков X11. Если
инструментов нет, он это скажет и остановится: `xcode-select --install`.

**Только оконный менеджер, из клона:**

```sh
make -C macos
sudo make -C macos install          # /usr/local/bin/digitwm
```

**Из brew:**

```sh
brew tap digitable-lol/digitwm https://github.com/digitable-lol/digitwm
brew install --HEAD digitable-lol/digitwm/digitwm
```

`--HEAD` — потому что выпуска с маковской целью ещё нет. Формула лежит в
`macos/digitwm.rb` и её тоже никто ни разу не запускал.

## Что видно при первом запуске

```
$ digitwm
```

1. macOS поднимает свой диалог: «digitwm хочет управлять этим компьютером с
   помощью функций универсального доступа». Ни одно окно ещё не тронуто. Apple
   про этот вызов пишет прямо, что запрос «происходит асинхронно и не влияет на
   возвращаемое значение», — поэтому следующее, что вы увидите:
2. digitwm говорит, что разрешения у него нет, называет, где выключатель, и
   выходит. Это не сбой: разрешение читается один раз, при запуске.
3. Вы включаете digitwm в **Системные настройки → Конфиденциальность и
   безопасность → Универсальный доступ** и запускаете снова.
4. `digitwm: 31 window(s) on the ribbon.` — и все открытые окна выстраиваются в
   колонки. Дальше процесс молчит, пока вы не нажмёте клавишу или не откроете
   окно.

**В Dock ничего не появляется, строки меню тоже нет.** У digitwm нет
собственного окна: он расставляет чужие. Остановить — Control-Option-Q или
Control-C в терминале, из которого он запущен.

**Запускать из терминала в вошедшем графическом сеансе.** Не по ssh и не из
демона launchd: процесс без связи с оконным сервером не может забрать
комбинацию клавиш, и digitwm говорит об этом словами, а не запускается глухим.

## Два разрешения, и почему спрашивают одно

Apple делит права на клавиатуру и окна надвое, и деление не то, которого ждёшь.
Из сессии WWDC, где это ввели: «там, где приложению, только слушающему события,
нужно разрешение на мониторинг ввода, приложению, изменяющему события, нужно
разрешение на универсальный доступ».

| Что делает программа | Что macOS спросит у пользователя |
|---|---|
| читает и пишет чужие окна через Accessibility API | **Универсальный доступ** |
| смотрит все клавиши через `CGEventTap`, даже ничего не меняя | **Мониторинг ввода** — другой выключатель, другой диалог |
| забирает одну комбинацию через `RegisterEventHotKey` | ничего |

Первое digitwm нужно, потому что двигать чужое окно — это оно и есть. Второго он
избегает тем, что берёт клавиши через `RegisterEventHotKey`, а не через event
tap; довод целиком — в шапке `macos/wsi_key.m`. Итого: **одно разрешение,
спрошенное один раз.**

Цена этого выбора записана, а не спрятана:

- `RegisterEventHotKey` — это Carbon, и инженеры Apple сами говорят, что честно
  рекомендовать его не могут: «намертво привязан к устаревшему Carbon
  toolbox». Современной замены, которая проглатывает клавишу без второго
  разрешения, нет.
- **macOS Sequoia отказывает горячей клавише, у которой из модификаторов только
  Shift и Option.** Таблица по умолчанию везде использует Control-Option и под
  запрет не попадает; строка `bind-key M-h ...` в `digitwmrc` — попадает, и digitwm
  предупреждает на этой строке, а не даёт отказу случиться молча.

Есть третье разрешение, которого digitwm не просит намеренно: **запись экрана**.
Содержимое окон он не читает, только прямоугольники.

## Клавиши

```
$ digitwm -k
```

печатает живую таблицу. По умолчанию:

| Клавиши | Что происходит |
|---|---|
| ⌃⌥ H / L | фокус на колонку левее / правее |
| ⌃⌥ K / J | фокус на окно выше / ниже в колонке |
| ⌃⌥⇧ H / L | унести окно в соседнюю колонку |
| ⌃⌥⇧ K / J | унести окно вверх / вниз по своей колонке |
| ⌃⌥⌘ H / L | поменять колонку местами с соседней |
| ⌃⌥ R | перебрать четыре ширины колонки |
| ⌃⌥ = / − | шире / уже |
| ⌃⌥ C | поставить ленту серединой на текущую колонку |
| ⌃⌥ F | снять окно с ленты в плавающий слой и обратно |
| ⌃⌥ Q | остановить digitwm |

**Это не те клавиши, что в X11, и так сделано намеренно.** `conf.c:280`
привязывает ленту к Mod4, «потому что upstream cwm оставляет её полностью
свободной». На маке Mod4 — это Command, то есть ровно наоборот, а регистрация
горячей клавиши забирает комбинацию у **всех** приложений сразу. Порт,
сохранивший X11-таблицу, при первом же запуске отобрал бы у всего стола
Command-H, Command-J, Command-K, Command-L, Command-C, Command-F, Command-R,
Command-минус и Command-равно. Control-Option — то, что macOS не трогает сам.

Вернуть X11-клавиши можно, записав их в `~/.digitable/digitwm/digitwmrc`; буквы
модификаторов те же, что уже описаны в `cwmrc(5)`:

| Буква | X11 | macOS |
|---|---|---|
| `S` | Shift | ⇧ Shift |
| `C` | Control | ⌃ Control |
| `M` | Mod1 (Alt) | ⌥ Option |
| `4` | Mod4 | ⌘ Command |
| `5` | Mod5 | — ничего; у мака их четыре |

Привязка на одном Command получит строку предупреждения о том, что она сделает с
остальной машиной. И всё равно будет выполнена.

## Какой файл читается и что из него

digitwm читает **тот же файл, что и X11-сборка**, и находит его тем же
поиском, — чтобы один файл описывал обе машины. Порядок, от сильного к
слабому:

| | файл | |
|---|---|---|
| 1 | названный ключом `-c` | сильнее всего остального |
| 2 | `$DIGITWMRC` | если переменная задана и непуста |
| 3 | `~/.digitable/digitwm/digitwmrc` | своё имя в каталоге, где это семейство инструментов держит настройки |
| 4 | `~/.cwmrc` | имя cwm: читается, чтобы конфигурация, написанная для cwm, продолжала работать, — и об этом говорится вслух, один раз, в stderr |

Порядок написан один раз — `confpath.c`, — и компилируется в оба двоичных
файла, а не переписан дважды; `tools/check-config-order.sh` задаёт обоим одни и
те же семь вопросов на каждый push. Мак, который молча читал бы не тот файл,
что рабочая станция, превратил бы «один файл описывает обе машины» в
предложение и только.

Прочитать весь этот файл он не может. В `cwmrc(5)` **34 директивы**; digitwm
выполняет **9**, а остальные **25** называет вслух, с причиной, на той строке,
где они стоят:

```
$ digitwm -n
/Users/you/.digitable/digitwm/digitwmrc: 12 directive(s): 6 taken, 5 X11's alone, 1 not understood
```

**Выполняются (9):** `ribbon`, `ribbonhide`, `ribbonwarp`, `ribbongap`,
`ribbonminwidth`, `ribbonminheight`, `ribbonwidths`, `bind-key`, `unbind-key`.

**Только X11 (25)**, по причинам — все четыре решены в
[macos.ru.md](macos.ru.md) до того, как всё это было написано:

- **на чужом окне нечего рисовать рамкой** — `borderwidth`, `activeborder`,
  `inactiveborder`, `urgencyborder`, `groupborder`, `ungroupborder`, `color`;
- **нет меню** — `font`, `fontname`, `selfont`, `menubg`, `menufg`;
- **нет групп**, потому что у Spaces нет публичного API — `sticky`,
  `autogroup`;
- **нет захвата указателя и нет EWMH** — `bind-mouse`, `unbind-mouse`,
  `snapdist`, `moveamount`, `htile`, `vtile`, `gap` (у
  `NSScreen.visibleFrame` Dock и строка меню уже вычтены, вычитать нечего),
  `command`, `wm`;
- **порт не читает класс окна** и потому не может сопоставить — `ignore`,
  `ribbonrule`.

Последняя пара — единственная в списке, которая является дырой, а не потерей.
`ribbonrule` кладёт названное приложение в выбранную колонку; на macOS для этого
нужен ещё один вызов через границу — спросить у окна заголовок или приложение, —
а `macos/wsi_platform.h` намеренно шириной в одиннадцать вызовов. Это названо
здесь, а не выдано за работающее.

`ribbonwarp yes` принимается и ничего не делает, о чём и сообщает: этот порт не
умеет двигать указатель вовсе. `wsi.h` разрешает ровно это — при условии, что и
фокус за указателем не ходит, — и порт берёт пару целиком.

Из **124 команд**, которые `bind-key` может назвать на X11 (`conf.c`,
`name_to_func`), здесь существуют **16**: пятнадцать команд ленты и `quit`.
Остальные просят рамку, группу, меню, перенос указателя или свойство EWMH.
Шестнадцать печатает `digitwm -k`.

## Когда не работает — узнать, какое имя отказало

```
$ digitwm -N
```

проходит по всем вызовам Apple, которые делает порт, в том порядке, в каком
доходит до них при работе, и печатает, кто ответил:

```
  [1] AXIsProcessTrustedWithOptions               answered  Accessibility granted
  [2] +[NSScreen screens], -frame, -visibleFrame  answered  2 display(s), first "Color LCD" 1512x982, workable 1512x944
  [2] NSWorkspace, NSRunningApplication           answered  31 window(s) taken onto the ribbon
  [2] +[NSEvent mouseLocation]                    answered  pointer at 812,443
  [1] AXUIElementCopyAttributeValue               answered  first window at 0,38 1512x944
  [2] AXUIElementIsAttributeSettable, Set...      answered  geometry accepted
  [2] AXUIElementPerformAction, kAXRaiseAction    answered  raise accepted
  [2] kAXMainAttribute, kAXFrontmostAttribute     FAILED    activation was refused
  [2] RegisterEventHotKey                         answered  CM-h taken
```

Строка `FAILED` называет вызов, а не симптом. Её и надо сообщать, а дальше в
этом разделе написано, чего стоит каждый.

**Чего `-N` поймать не может, и что ловит вместо него.** Опечатка в имени или
неверный список аргументов до запуска не доживают: они падают при первой же
встрече файла с настоящими заголовками Apple — ошибка компиляции с номером
строки, до того как что-то произойдёт с чьими-то окнами. Это самый дешёвый вид
отказа, и порт устроен так, чтобы отказывать именно им: ни в `macos/wsi_ax.m`,
ни в `macos/wsi_key.m` нет ни одной числовой константы Apple, только имена, —
так что тихая ошибка им недоступна.

### Три вещи, которые откажут первыми

**1. `macos/wsi_key.m` не соберётся.** Apple убрала справочник Carbon Event
Manager: страница документации отдаёт 404, а архивное руководство про горячие
клавиши не говорит ничего. Единственная страница Apple, где эти имена ещё
перечислены, печатает их в **swift-проекции**, то есть типы аргументов и их
порядок — Apple, а **си-объявлений Apple нигде больше не публикует**. Заглушка в
`macos/stub-build.sh` написана по этим типам; если настоящий заголовок с ними
разойдётся, компилятор скажет об этом на строке.

**2. Клавиши регистрируются и не приходят.** digitwm — обычный исполняемый файл
без пакета приложения. **Apple не документирует ничего** о том, получает ли
программа командной строки без пакета события горячих клавиш Carbon. Что Apple
говорит про соседний случай, про AppKit, — не обнадёживает: инженер пишет, что
обработка событий AppKit «может не работать, потому что может полагаться на
работающую машинерию AppKit», и что программе без пакета, желающей события
AppKit, нужны упаковка как у приложения и `NSApplicationMain`. Это AppKit, а
здесь Carbon, и порт отказывается переносить одно на другое молча — поэтому
названо здесь.

*Симптом:* `digitwm -N` пишет `RegisterEventHotKey answered`, окна расставляются
правильно, ни одна клавиша ничего не делает. *Лечение, по возрастанию цены:*
вызвать `-[NSApplication run]` вместо ручного проворачивания цикла; если не
поможет — положить digitwm в пакет `.app` с `LSUIElement` и поднять AppKit как
положено. И то и другое — правки в `macos/wsi_key.m` и `macos/wsi_run.c`, ленту
не трогает ни одна.

**3. Активация отвергнута.** `kAXFrontmostAttribute` и `kAXMainAttribute`
существуют, и Apple пишет, что они значат; чего Apple **не** пишет — какого типа
значение в них класть, и порт кладёт `kCFBooleanTrue` на том основании, что
парные константы AppKit документированы как `NSNumber`. Имена другие, значит это
догадка. *Симптом:* окна встают по колонкам, а клавиатура остаётся там, где
была. *Лечение уже названо в [macos.ru.md](macos.ru.md)*: приватный
`_SLPSSetFrontProcessWithOptions`, объявлять который из воздуха дерево
отказывается и объявит со ссылкой в тот день, когда он понадобится.

### Чего стоит каждый отказ

| Что отказало | Что перестаёт работать | Что работает всё равно |
|---|---|---|
| `AXIsProcessTrustedWithOptions` | всё | ничего — это и есть разрешение |
| `NSWorkspace` / `NSRunningApplication` | окна не находятся вообще | ничего |
| `NSScreen screens` / `frame` | ленты нет: её негде разложить | ничего |
| `NSScreen localizedName` | два одинаковых монитора становятся одним именем и одной лентой | один монитор |
| `AXUIElementCopyAttributeValue` | порт не читает прямоугольник окна | ничего |
| `AXUIElementIsAttributeSettable` / `SetAttributeValue` | окна никогда не двигаются | раскладка считается и не применяется |
| `AXUIElementPerformAction` (raise) | перекрывающиеся окна остаются не в том порядке | колонки, которые не перекрываются |
| `kAXMainAttribute` / `kAXFrontmostAttribute` | клавиатура не идёт за фокусом | вся раскладка |
| `RegisterEventHotKey` | нет команд | расстановка окон по мере открытия и закрытия |
| `AXObserverRemoveNotification` | ушедшее окно стоит немного лишней работы | всё |
| `CFRunLoopRemoveSource` | у закрытого приложения течёт наблюдатель | всё |

## Что проверено здесь, а что не проверено нигде

Три команды на машине, где macOS нет, и их числа:

```
$ sh macos/check.sh 400
```

- лента поверх macOS-порта против X11-двоичного файла: **400 случаев, 2680
  окон, 0 расхождений**; из них **1213 окон** сверены второй раз с тем, что
  реально держит оконная система, **0 расхождений**;
- обратный механизм, один сценарий дважды: с пометкой **40 выдач, 40 извещений,
  40 признаны своими, 0 приняты за чужие, 5 кругов до тишины**; без неё **9968
  выдач, 9967 приняты за чужие, 1200 кругов и тишины нет**;
- парковка с `ribbonhide`: **2 окна внутри вьюпорта, 18 за краем, по 1 пикселю
  от каждого видно**;
- последовательность запуска, настройки и разбор клавиш поверх оконной системы
  из памяти: образец настроек из **12 директив → 6 принято, 5 отдано X11, 1 не
  понята**; **6 окон в 6 колонок, 0 разошлось**; **16 привязок, 1 отвергнута и
  названа**; клавиша переносит фокус, клавиша расширяет колонку, клавиша уносит
  окно; чужое перемещение возвращается; появляется второй монитор — и вторая
  лента вместе с ним;
- и двоичный файл целиком **слинкован**: настоящий `main()` и все объектные
  файлы, которые собирает `macos/Makefile`, кроме ровно двух — `wsi_ax.m` и
  `wsi_key.m`, вместо которых оконная система из памяти и подделка клавиатуры.
  Это максимум того, что можно ответить на вопрос «соберётся ли на маке», не
  имея мака: набор объектных файлов полон и сходится.

```
$ sh macos/stub-build.sh
```

собирает `wsi_ax.m` и `wsi_key.m` против заглушек ApplicationServices, AppKit и
Carbon с `-Wall -Wextra -Werror`. Проверка фальсифицируема и была
фальсифицирована нарочно: `kVK_ANSI_H`, написанное как `kVK_ANSI_HH`, падает на
`macos/wsi_key.m:122`.

**Здесь не проверено никогда и никакой аккуратностью не проверяется:** верны ли
заглушки; собирается ли хоть один из двух `.m` против настоящих заголовков
Apple; работает ли `macos/Makefile`; тот ли флаг `-sectcreate __TEXT
__info_plist` (Apple документирует саму *секцию* и настройку Xcode, которая её
делает, а страницу руководства линкера больше не хостит); доходит ли хоть одна
горячая клавиша; мелькание в миллисекундах; цена одного кругового рейса в живое
приложение; молча ли отказывает выдача геометрии.

## Доставка и ловушка в ней

**Mac App Store для этой программы закрыт правилом самой Apple.** Apple
перечисляет «использование accessibility API в ассистивных приложениях» среди
запрещённого в песочнице, а магазин без песочницы не принимает. Значит digitwm —
обычный исполняемый файл со вшитым в секцию `__TEXT,__info_plist` `Info.plist`
(та форма, которую Apple документирует для однофайловых инструментов), и его
дорога — brew.

**Ловушка: разрешение запоминается по подписи.** `make -C macos` подписывает
ad-hoc (`codesign --sign -`), а ad-hoc-подпись — это хеш двоичного файла, то
есть каждая пересборка для macOS уже другая программа, и диалог возвращается.
Пересобирать дважды в день — отвечать на него дважды в день.

Выход — своё постоянное удостоверение подписи. Создать самоподписанный
сертификат Code Signing в «Связке ключей» (Ассистент сертификации → Создать
сертификат, тип *Подпись кода*), затем:

```sh
make -C macos SIGNID="Имя вашего сертификата"
```

— и разрешение переживает пересборки. Это обычная практика ровно для этой
задачи, и она ни разу не была выполнена в этом проекте.

## Чего не будет

Шесть из этого разобраны в [macos.ru.md](macos.ru.md) — измерением или
названным отсутствием, — и ни одно не является временным состоянием работы:

1. **окно дёрнется.** Оно появляется там, куда его поставило приложение, и уже
   потом уезжает в свою колонку: у macOS нет аналога `MapRequest` из X11, а
   `AXObserverCallback` объявлен `void`;
2. **`ribbonhide` оставляет полоску в 1 пиксель.** macOS не даёт увести окно за
   экран целиком;
3. **групп нет.** У Spaces нет публичного API;
4. **полноэкранное окно не на ленте.** Оно живёт в своём Space, и политика
   вставки это уже предусматривала;
5. **родные вкладки ломаются.** Terminal.app со вкладками — одно окно для
   Accessibility API и несколько для вас;
6. **у активного окна нет рамки.** На чужом окне рисовать нельзя. Как ещё
   отмечать окно с фокусом — отдельное решение владельца, не часть этого
   переноса.

И два, которые добавляет этот документ:

7. **указатель никогда не переносится за фокусом** — вызова для этого в
   публичном API нет, и фокус за указателем тоже не ходит. Одно решение, обе
   половины;
8. **окно приложения, которого секунду назад не было запущено, попадает на
   ленту с опозданием до секунды.** Порт спрашивает, кто запущен, по часам, а
   не подпиской, и шапка `macos/wsi_ax.m` говорит почему, чего это стоит и
   какие два документированных имени извещений это заменяют.
