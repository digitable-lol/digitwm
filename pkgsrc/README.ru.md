# Порт для pkgsrc

**English version: [README.md](README.md).**

`wm/digitwm` — пакет pkgsrc для одного только оконного менеджера: без сессии,
без тем, без агента. Лежит он здесь, а не в pkgsrc, потому что ещё не подан
туда; скопируйте и соберите:

```sh
cp -r pkgsrc/wm/digitwm /usr/pkgsrc/wm/digitwm
cd /usr/pkgsrc/wm/digitwm
make makesum          # запишет distinfo по релизному архиву
make install
```

## Почему нет `distinfo`

В `distinfo` лежат контрольные суммы дистрибутивного файла. **Релизного архива
пока нет** — тег не выложен, — значит, считать сумму не с чего, а выдуманный
хеш был бы хуже отсутствующего файла: он свалил бы сборку на этапе загрузки с
сообщением о порче архива вместо сообщения об отсутствующем релизе.

С какого именно файла будет сумма — уже определено. В `DISTNAME` стоит
`digitwm-0.1.0`, в `GITHUB_TAG` — `v${PKGVERSION_NOREV}`, а для тега
`mk/fetch/github.mk` в pkgsrc собирает имя как `${DISTNAME}${EXTRACT_SUFX}`:
будет загружен `https://github.com/digitable-lol/digitwm/archive/v0.1.0.tar.gz`
и сохранён как `digitwm-0.1.0.tar.gz`. Отсюда два шага, ровно в таком порядке:

1. владелец релиза выкладывает тег `v0.1.0`;
2. в дереве pkgsrc файл создаётся одной командой:

```sh
cd /usr/pkgsrc/wm/digitwm && make makesum
```

Она запишет `distinfo` со строками `BLAKE2s`, `SHA512` и `Size` для
`digitwm-0.1.0.tar.gz`. Шаг 2 невозможен раньше шага 1: версия в Makefile —
та, которую понесёт первый релиз, а не уже опубликованная.

## Что проверено, а что нет

Всё, что ниже, измерено на Linux. **Машины с NetBSD здесь нет**, поэтому ничто
из перечисленного не означает, что порт собран средствами pkgsrc.

**Измерено.** Из корня репозитория, в пустой каталог, теми самыми флагами,
которые передаёт пакет (`INSTALL_MAKE_FLAGS`: `PREFIX` и
`MANPREFIX=${PREFIX}/${PKGMANDIR}`):

```sh
make                                                        # код возврата 0
make install PREFIX="$PWD/stage" MANPREFIX="$PWD/stage/man"
( cd stage && find . -type f -o -type l )
```

`make` завершается с кодом 0 (при четырёх предупреждениях компилятора), а
установка кладёт ровно три файла:

```
bin/cwm
man/man1/cwm.1
man/man5/cwmrc.5
```

Это и есть `PLIST`, строка в строку, и сверено в обе стороны: не ставится
ничего, чего нет в `PLIST`, и не перечислено ничего, что не ставится. `man/` в
начале строки `PLIST` — не догадка о раскладке: pkgsrc сам заменяет его на
`${PKGMANDIR}/` (`mk/plist/plist-man.awk`), поэтому тот же `PLIST` верен и при
`PKGMANDIR` равном `man` (значение по умолчанию), и при `share/man`; прогнаны
оба, и оба дали те же три файла. `DESTDIR` тоже прогнан и уважается; пакету не
нужно передавать его самому — pkgsrc добавляет его к команде установки
(`mk/install/install.mk`).

**Измерено: `pkglint` чист, кроме отсутствующего `distinfo`.** `pkglint` —
переносимая программа на Go, и NetBSD ей не нужна: нужно лишь дерево pkgsrc,
из которого она читает инфраструктуру:

```sh
go install github.com/rillig/pkglint/v23/cmd/pkglint@v23.21.1
cp -r pkgsrc/wm/digitwm /usr/pkgsrc/wm/digitwm
cd /usr/pkgsrc/wm/digitwm && pkglint -Wall .
```

На дереве pkgsrc от апреля 2026 года (`mk/bsd.pkg.mk` 1.2061) версия 23.21.1 —
та самая, которую пакует сам pkgsrc, — печатает одно предупреждение и больше
ничего:

```
WARN: distinfo: A package that downloads files should have a distinfo file.
```

то есть тот самый отсутствующий `distinfo` из раздела выше, который никакой
аккуратностью не убрать раньше тега. Зависимости, категории, лицензия,
написание `MASTER_SITES` и `PLIST` проходят проверку.

**Не проверено.** Сам порт средствами pkgsrc ни разу не собирался и не
ставился: `bmake` и `pkgin` здесь отсутствуют, как и машина с NetBSD. Ниже —
команды для того, у кого она есть; выполнять в скопированном каталоге пакета
`/usr/pkgsrc/wm/digitwm`:

```sh
make makesum      # только после того, как выложен v0.1.0; создаёт distinfo
make              # порт ни разу не собирался средствами pkgsrc
make install      # порт ни разу не ставился средствами pkgsrc
make package      # двоичный пакет ни разу не собирался
make clean        # и затем проверить, что дерево осталось прежним
```

и, после установки, что оконный менеджер вообще поднимается на NetBSD:

```sh
cwm -n            # называет файл настроек, который он бы прочитал
cwm               # и затем, на дисплее, что он поднимается
```

Не считайте порт проверенным, пока `make install` из этого списка не пройдёт
на машине с NetBSD. Написанное здесь верно по измерению там, где измерение
приведено, и по руководству везде, где не приведено.

## Имя двоичного файла

Двоичный файл по-прежнему называется **`cwm`**, и страницы руководства тоже —
чтобы конфигурация, написанная для cwm, и всё написанное про cwm переносилось
без правок; сам файл читается сперва из `~/.digitable/digitwm/digitwmrc`, а
затем из `~/.cwmrc` (`cwm(1)`, раздел FILES). Поэтому в
пакете стоит `CONFLICTS+= cwm-[0-9]*`: рядом эти два пакета не встанут.

Переименовывать ли форку свой двоичный файл — решение с ценой по обе стороны:
переименование ломает всякий конфигурационный файл, сессионный скрипт и
`.xinitrc`, где уже написано `cwm`; сохранение имени мешает поставить оба
пакета вместе. Это решение владельца, а не порта.

## Зависимости и почему их так мало

Пакет объявляет три библиотеки через buildlink и два инструмента — и ничего
больше:

```
USE_LANGUAGES=	c
USE_TOOLS+=	pkg-config yacc
.include "../../x11/libX11/buildlink3.mk"
.include "../../x11/libXft/buildlink3.mk"
.include "../../x11/libXrandr/buildlink3.mk"
```

Это тот же список, который `bootstrap.sh` ставит для сборки из исходников:
компилятор C и make, заголовки x11, xft и xrandr, `bison` и `pkg-config`, —
только записанный так, как ждёт pkgsrc. `USE_TOOLS+= yacc` покрывает то, что
`bootstrap.sh` называет `bison`: на NetBSD он разрешается в `/usr/bin/yacc` из
базовой системы, в остальных случаях pkgsrc подтягивает `devel/bison`, и
большего разбору конфигурации не нужно — `parse.y` пользуется только
классическими конструкциями yacc. `USE_TOOLS+= pkg-config` разрешается в
`devel/pkgconf`. Строка `DEPENDS` не нужна: три buildlink-подключения и есть
полноценные зависимости — и на сборку, и на запуск, — а никаких заголовков X
сверх этих трёх библиотек в исходниках нет.

Всё, что `bootstrap.sh` ставит сверх этого — редактор, терминал, оболочка,
мультиплексор, темы, агент, — намеренно не попадает в `DEPENDS`; почему, см.
ниже. Модели FTS из `fts/` проверяются в CI, не собираются и не ставятся —
именно это избавляет пакет от зависимости на Node в NetBSD.

## Не оконный менеджер, а всё окружение

Порт ставит оконный менеджер и больше ничего. Окружение, ради которого он
задуман — редактор, терминал, оболочка, мультиплексор, темы Digitable Focus и
агент Digit, — ставит [`bootstrap.sh`](../bootstrap.sh) в корне репозитория, и
он же и есть та «одна команда» из `DGT-WM-12`:

```sh
sh bootstrap.sh --plan     # посмотреть, что будет сделано
sh bootstrap.sh            # сделать
session/verify.sh          # проверить, что получилось
```

Разделение намеренное. Пакетный менеджер ставит программы, а сессия
раскладывает конфигурацию в домашнем каталоге пользователя, и делать это из
post-install пакета она не вправе.
